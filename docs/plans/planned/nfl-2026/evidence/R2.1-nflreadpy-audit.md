# R2.1 nflreadpy currency and capability audit

Status: Complete

## Scope and direct dependency evidence

The R2 wave packet requires an nflreadpy currency/capability audit with typed
freshness and failure metadata. Direct R1 evidence in
`R0.3-salvage-ledger.md` identifies provider currency, skipped-year handling,
typed timestamps, and explicit failure metadata as R2.1 inputs. The existing
provider contract and normalization tests were preserved.

## Delivered contract

- `ProviderCapabilities` records provider name, supported datasets, current-
  season support, and the source-license note.
- `FreshnessMetadata` records requested and available seasons, an aware UTC
  retrieval timestamp, and `complete`/`partial`/`empty` status.
- `FailureMetadata` records typed unavailable/error classification, exception
  type, safe message text, and optional season.
- `LoadResult` retains the existing `data` and `skipped_years` fields while
  carrying the typed metadata. Normalization preserves metadata.
- nflreadpy responses now identify missing seasons even when a multi-season
  response is partial, and retain typed unavailable failures.

## Diagnosis packet — blocked after repeated review repairs

Status: Complete after authorized diagnosis follow-up

The second independent review reported materially similar gaps in three
areas: typed failure metadata is not complete for every provider failure path,
legacy-provider parity is incomplete, and the audit lacks the approved
snapshot-fixture contract. Per the orchestration rule, no third repair was
attempted. The operator subsequently authorized the narrow follow-up below.

### Exact reproductions

1. `NFLReadPyProvider.load_weekly([2025])` with a stub that raises
   `RuntimeError("500 Service Unavailable")` raises the raw exception. The
   non-404 branch in `_fetch_with_fallback` deliberately re-raises, so no
   `FailureMetadata(kind="error", ...)` or `LoadResult` is produced.
2. `NflDataPyProvider` wraps successful frames with freshness metadata, but its
   legacy exception paths (`_require_module` and loader exceptions) still raise
   directly and do not return typed failures. Its capability matrix is a
   declaration rather than evidence-backed capability observations.
3. The tests use in-memory stubs only. There is no committed, immutable offline
   snapshot fixture and hash/manifest assertion proving the audit matrix against
   a frozen provider response. This leaves the fixture-contract acceptance
   criterion unresolved.
4. Evidence is stale/incomplete: `Repair commit: ` remains
   `PENDING_REPAIR_COMMIT`, while the actual repair commit is `4620000`.
   Rewriting that line after committing would require another commit and would
   change the hash again; the post-commit evidence policy must define the
   expected traceability mechanism.

### Root causes

- The initial contract modeled 404/skipped seasons but not typed non-404
  failures or provider-level failures.
- Capability parity was added as static metadata without a shared helper that
  normalizes every provider's success and failure responses.
- Fixture provenance and post-commit evidence sequencing were not specified
  before implementation, so tests cannot prove reproducibility independently
  of monkeypatched loader behavior.
